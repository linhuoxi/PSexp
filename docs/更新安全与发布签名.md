# 更新安全与发布签名

适用范围：2026-10-30 的当前源码。客户端强制验签需要编译进新的 EXE 才能生效；旧 EXE 不会因为服务器增加签名字段就自动具备验签能力。本次未编译、未运行软件测试，没有发布新 EXE。

## 开源内容与发布身份

源码、签名算法、协议和公钥可以公开。公钥只能核对签名，不能代替私钥给篡改的清单签名。发布私钥不进入应用、不放服务器，也不纳入 Git。

普通用户和开发者不需要官方私钥即可运行、修改或通过公开 `编译.bat` 构建。Fork 可以采用自己的域名、公钥和私钥；官方私钥只用于官方更新来源的认证。

## 保护什么、有哪些边界

旧流程只校验 EXE 大小、SHA256 和版本。若攻击者能同时改服务器上的 EXE 与清单，这些检查本身不能认证发布者。

新流程固定使用应用内嵌公钥，验证清单签名后才使用下载地址、版本、SHA256、大小、说明和运行时要求。只有哈希相同且版本正确的文件才能继续安装。

它防范更新服务器单独失守后伪造新清单和更新包，不防范发布者本机、源码构建环境或签名私钥已经失守；不能阻止服务器停止服务或隐藏新版。当前没有签名有效期和完整的防冻结协议。高于当前客户端版本的历史有效签名可能被重放，客户端不会安装低于或等于自己的版本。

这里是更新元数据签名，没有给 EXE 做 Windows Authenticode 代码签名，不应宣称解决了 SmartScreen 或所有软件安全问题。

## 签名协议 v1

`version.json` 保留旧客户端读取的平铺字段，并增加 `signed_update` 对象：

| 字段 | 规则 |
| --- | --- |
| `schema` | 整数 1 |
| `key_id` | 必须匹配应用内嵌信任锚的标识 |
| `algorithm` | 固定 `RSA-SHA256-PKCS1`，不由服务器自由选择算法 |
| `payload` | 实际元数据 JSON 的原始 UTF-8 字节，Base64 编码 |
| `signature` | 3072 位 RSA、SHA256、PKCS#1 v1.5 的签名，Base64 编码 |

参与签名的字节是：`UTF8("PSexp update manifest v1\n")` 加上解码后的 `payload` 原始字节。这里 `\n` 指一个 LF 换行字符。所有影响更新行为的字段都位于 payload 中，不依赖两端重新排序 JSON 或重新序列化后的文本。

新客户端完全忽略外层平铺字段，只从验签通过的 payload 创建不可变 `UpdateManifest`。因此攻击者修改外层 `download_url`、`sha256` 或版本并不能改变新客户端的实际更新目标。缺签、坏签、未知密钥和不支持的签名格式都拒绝，没有回退到无签名清单的兼容开关。

外层字段仅照顾旧客户端的可读性；旧客户端仍然不验证签名。首次升级到支持验签的版本，应通过可信源码构建或确认的 GitHub Releases 获取，不能宣称旧客户端已被远程修好。

## 源码与信任锚

- [UpdateSignature.cs](../PSdodo/Services/UpdateSignature.cs)：限制格式与长度、加载固定公钥、校验签名、读取认证内容。
- [UpdateService.cs](../PSdodo/Services/UpdateService.cs)：验签后的 URL/版本/大小校验、下载、EXE 校验和安装。
- [公钥资源](../PSdodo/Resources/Updates/update-public-key.json)：只含 key ID、算法、公钥 XML，由项目嵌入应用。
- [UpdateSigning.ps1](../tools/UpdateSigning.ps1)：公开的私钥加载、匹配检查与签名函数。
- [Initialize-UpdateSigning.ps1](../tools/Initialize-UpdateSigning.ps1)：首次建立独立发布身份；已有私钥或公钥时拒绝覆盖。

应用不从更新服务器下载或信任新的公钥。改变源码中的信任锚需要构建新版本；仅修改服务器清单不能偷偷换公钥。

## 私钥存放与换机

默认私钥路径为 Windows 当前用户本地应用数据目录下的 `PSexp/ReleaseSigning/update-key.dpapi`（通常为 `%LOCALAPPDATA%/PSexp/ReleaseSigning/update-key.dpapi`），位于仓库和 OneDrive 项目之外。路径通过 Windows `LocalApplicationData` 已知目录解析，避免启动器遗留的 `LOCALAPPDATA` 环境变量指向错误位置。目录 ACL 限制为当前 Windows 用户，私钥以 Windows DPAPI `CurrentUser` 范围加密。内存中解密后用于签名，字节缓冲使用后清理；不输出私钥文本。

环境变量 `PSexpSigningKeyFile` 可以显式指定受保护私钥文件；显式指定错误时会报错，不偷偷切换到其他密钥。不得把这个文件搬进源码或服务器。发布脚本会核对私钥对应的公钥与仓库信任锚一致，缺钥或不匹配即停止，不自动重建一个新的官方密钥。

DPAPI 与原 Windows 用户环境绑定：仅复制 `.dpapi` 文件到另一台机器，不保证能解密。当前工具没有便携私钥导出和自动密钥轮换功能。换机、重装系统前应备份能恢复该 Windows 用户及 DPAPI 资料的原环境，或另行完成受控的私钥迁移；不要先抹掉旧环境再尝试重新生成。原私钥丢失后，新钥无法给已内置旧公钥的客户端直接建立信任，需要可信渠道重新分发客户端。

加密存放不能防止已控制同一 Windows 用户会话的恶意程序调用解密，所以发布机本身仍须保护。签名私钥和服务器 SSH 登录密钥是两种不同凭据，不应混用。

Fork 第一次初始化时，应先明确移除自己分支中的官方公钥资源，再运行初始化工具生成自己的配对身份；不要在官方分支上随意更换信任锚。公开构建入口本身不要求初始化签名身份。

## 发布流程

作者本机外层 `release-tools/Release.ps1` 支持只读 `-Phase CheckSigning -Repository <源码目录>`：只检查原签名身份，不预留版本、不编译、不推送、不部署。检查会显示实际 Windows 账户、受保护密钥路径及路径来源，不输出私钥。缺失、无法解密和公钥不匹配会给出不同原因；签名失败退出码为 21，外层 BAT 单独显示签名问题，不再误报为 GitHub/版本号问题。检查成功只表示当前签名环境可用，不能证明另一账户或启动器下也可用。

作者本机外层 `release-tools/Release.ps1` 在准备版本和发布前检查签名身份；`Deploy-Server.ps1` 用实际 EXE 的版本、大小和 SHA256 生成元数据并签名。工具和服务器连接配置仍在仓库外，不随 Git 推送。

顺序为：确认源代码与身份 → 递增正式版本并构建 → 发布 GitHub 附件 → 本机签名元数据 → 上传成品和已签清单 → 服务器核对文件哈希 → 最后原子切换清单。缺少或不匹配的签名身份应在发布前阻止流程。不能在服务器上自动给上传的任意包签名。

签名不是混淆。客户端、验证逻辑和公钥都保持开源，发布者的私钥仅用于签发更新。

## 更新服务器的隔离

PSexp 下载网址仍为 `https://yusnip.top/psexp/...`，静态内容改由独立的 `/srv/psexp-updates/` 提供。目录 root 所有、755；文件 root 所有、644。其父目录不可被 Web 用户写入，防止通过重命名共享站点子目录绕过子目录只读保护。

Nginx 只为 `/psexp/` 配置独立静态映射，关闭目录列表并限制为 GET/HEAD。发布账号通过已有受控部署流程安装文件，Web 进程没有该目录的写权限。共享网站的其他内容、SSH 和防火墙没有因此一起改动。

迁移前保存了原站点配置与清单，配置检查失败会恢复；现有 3.0.0 EXE 的内容、文件大小、哈希和版本没有替换，只给对应清单补上签名。源码中的客户端保护仍待用户自行编译后的新版生效。

## 维护时应核对的事项

发布时核对本机签名身份、公钥资源、真实成品版本/大小/哈希、清单签名及公网结果；发布工具拒绝无签名，并不代替 Photoshop 和窗口功能验收。

不要为了排查问题打印私钥、把 DPAPI 解密文本写日志、把私钥交给服务器，或临时关闭客户端验签。服务器仍可能发生停机或拒绝服务；签名只保证客户端能识别认可的发布内容，不保证网络永远可用。
